# Document names and transfer performance (2026-10-28)

## Progressive saved editor (2026-10-29)

Selecting Edit now opens an `EditableDocument` shell synchronously from the already-loaded metadata; `SavedDocumentScreen` never waits for image transfers. Each placeholder has a private thumbnail URL and explicit loading/failed state. The editor owns a sequential page queue: it fetches the original/rendered pair for one page, publishes that page immediately, then moves to the next. Ready page tools work while later pages load; PDF export remains disabled until every remaining page is ready. Loading completion changes only its target page and never resets edited pages or the name.

Failed pages have an individual retry action, placed next in the queue. Deleted pages are removed from the queue, current transfers are aborted when removed, and reset/unmount cancels all work. Controller identity prevents stale completions; the reducer ignores removed IDs. Retries and loading updates do not mark a document dirty. The older all-at-once `documentApi.edit` helper remains compatible and shares the same page decoder.

Regression coverage uses unresolved page promises to verify an immediate editor shell, one active page, early editing, export gating, per-page failure/retry, deletion without resurrection, unmount cancellation and StrictMode effect cleanup. The complete 644-test suite passed before the additional StrictMode regression; all five progressive-editor tests passed afterward, with lint/typecheck/build.

CamScanner's official [offline guide](https://blog.camscanner.com/2026/09/23/how-to-use-camscanner-offline-practical-ways-to-access-and-manage-documents-without-internet/) documents locally saved/offline documents and later cloud sync. It does not disclose its internal scheduler or cache implementation. Our change adopts immediate UI plus incremental availability; it does not introduce persistent offline storage. The existing in-memory editor already remains intact when returning from its own PDF reader. Network first-page latency and cold server startup still apply when opening a document from the library.

The image editor exposes a document-name field before PDF generation. Saved readers display the name and allow renaming through `PATCH /api/v1/documents/{id}` with `{name, revision}`. The server validates names using the same rules as full saves, checks ownership and optimistic revision, and changes only database metadata. PDF/image bytes and private asset identities stay unchanged. Renaming no longer requires PDF generation or a multipart upload. Existing clients can continue to use full PUT saves.

Opening the editor previously awaited original then rendered image for every page in sequence. Two page workers now fetch at most four images concurrently, preserve order, and cancel remaining transfers on failure or navigation. The total decoded image policy is unchanged. Cloud saves use four file streams and a single HTTPX client per batch instead of a separate client/connection for each sequential upload. Staged garbage tracking, atomic publication and previous-version protection remain in force; all upload workers finish before local staging is removed.

Regression checks verify bounded downloads and ordering, metadata-only rename, unchanged cloud bytes after rename, stale revision/ownership rejection, and one shared client for a seven-file batch. No claim of a fixed speed multiplier is made: network conditions, file sizes, image processing and free-host resource limits still affect elapsed time. Fresh image processing and edited PDF encoding still run on the device; full content saves still upload every page. Opening saved metadata still requires a server request. These are remaining performance limits, not hidden background-save shortcuts.

Verification: 639 full frontend tests passed before the last saved-reader rename test was added; 20 focused tests passed afterward. Lint and production build passed. Backend has 33 passing tests; SQLite, PostgreSQL and container CI passed for deployed BE `fd44911`, pinning FE `55acbea`. Read-only HTTP comparison on Render used the same two-page QA document and four image assets: sequential 12.88 seconds, four concurrent transfers 4.00 seconds, identical byte counts. This single sequential-then-parallel sample includes network variability and connection warming; it measures transfer time, not PDF encoding, UI rendering, or a guaranteed end-to-end speedup.

The hosted UI renamed an existing document while its PDF asset URL stayed unchanged, opened its editor with the saved name, changed the name before PDF export, saved successfully as revision 5 of the same document, and displayed the new name in the library. Physical phone timing remains unverified. Cross-session handoff was saved through AgentMemory's local fallback; its server did not confirm the save.
